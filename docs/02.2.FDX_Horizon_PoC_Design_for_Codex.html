02.2 FDX Horizon PoC Design for Codex

聚焦 Layer 1 → Layer 2 的业务交互、歧义澄清与语义表达，并以预置模板方式快速展示 Layer 3 产物。 当前阶段不追求真实部署，也不要求首先实现完整的确定性编译器。

完全离线 HTML · 生成日期：2026年8月1日

本 PoC 的第一目标不是“把 DSL 编译到所有 Runtime”，而是证明： 业务人员能够通过自然语言与系统交互，逐步形成一份清晰、无歧义、可审阅、可图形化的 Fraud Decision Specification。 Layer 3 暂时可以采用预置模板和 shortcut 映射来展示效果。

一、PoC 聚焦范围

当前必须做好

  • 自然语言业务意图输入
  • 识别规则、模型、阈值与动作
  • 检测歧义与缺失信息
  • 生成 clarification questions
  • 形成统一 DSL / IR
  • 生成可读的决策流程图
  • 业务人员可确认或修改

当前可以简化

  • Layer 2 → Layer 3 使用固定模板
  • 不需要先实现通用编译器
  • 不需要接入真实 GCP / AWS / Flink
  • 不需要部署到正式 Runtime
  • 不需要处理所有 Fraud Scenario
  • 不需要先解决性能、HA、RBAC
PoC 判断标准： 用户是否能够看懂“原始英文 → 澄清问题 → DSL → 决策图 → 示例技术产物”的完整变化， 并能够指出哪里不符合其业务意图。

二、建议用于 Demo 的规则 + 模型组合场景

1. Business Intent 示例

Decline the transaction immediately if the merchant is on the known fraudulent merchant list
or if the device ID is on the known fraudulent device list.

Otherwise, score the transaction using our in-house Card Fraud Detection model.
The model returns a score from 0 to 999.

Decline the transaction when the score is between 900 and 999.
Refer the transaction for review when the score is between 800 and 899.
Otherwise, approve the transaction.

这个示例符合当前常见的业务实践：

  • 先执行强规则，例如黑名单直接命中；
  • 规则未命中时再调用模型；
  • 模型输出分数后，再通过分数区间规则决定动作；
  • 最终输出 decision、score、reason code 和 explanation。
这个场景足够简单，业务人员容易理解；同时又能够验证 规则、名单、模型调用、分数区间和决策动作五种关键语义。

三、Layer 1：Business Authoring 与澄清交互

1. 系统从英文中初步识别的内容

强规则

Merchant blacklist 命中 → DECLINE

强规则

Device blacklist 命中 → DECLINE

模型

Card Fraud Detection Model，输出 0–999

分数规则

900–999 → DECLINE

分数规则

800–899 → REFER

默认动作

其他情况 → APPROVE

2. 系统应主动提出的澄清问题

  1. Merchant blacklist 的正式名称、版本和 lookup key 是什么？例如使用 merchant_id 还是其他标识。
  2. Device blacklist 使用哪个字段？例如 device_id、device fingerprint 或 token。
  3. 两个黑名单命中时，是否需要区分不同 reason code？
  4. 名单查询失败时采用 fail-open 还是 fail-closed？
  5. Card Fraud Detection 模型的正式模型 ID 和版本是什么？
  6. 模型所需特征缺失时，是调用 fallback 规则、返回错误，还是 REFER？
  7. 分数区间是否包含边界？例如 900 是否属于 DECLINE。
  8. 模型分数低于 800 时是否一律 APPROVE，还是仍可能由其他策略处理？
  9. 是否需要返回 rule hit、model score、decision reason 和 explanation？

3. Layer 1 推荐界面结构

左侧：Business Intent

  • 英语自然语言输入框
  • 可选择现有 feature / list / model
  • 显示识别到的业务对象
  • 显示系统提出的问题

右侧：Clarified Intent

  • 用户逐项回答
  • 系统实时更新结构化意图
  • 标记仍未确认的字段
  • 完成后进入 Layer 2 Review

四、Layer 2：Fraud Decision DSL / IR 示例

第一版建议使用 YAML 作为可读的文本表现形式，但内部概念应当是统一的 Canonical Semantic Model。 YAML、表单和 DAG 都只是它的不同视图。 

spec_version: "0.1"

decision_strategy:
  id: card_fraud_rule_model_demo
  name: Card Fraud Rule and Model Decision
  description: >
    Decline known fraudulent merchant or device transactions.
    Otherwise invoke the in-house card fraud model and decide by score bands.

input:
  event_type: card_transaction
  event_time_field: transaction_time

entities:
  merchant:
    key_field: merchant_id
  device:
    key_field: device_id

resources:
  lists:
    - id: fraudulent_merchant_list
      type: blacklist
      lookup_key: merchant_id
      version: "demo-v1"
      on_lookup_error: REFER

    - id: fraudulent_device_list
      type: blacklist
      lookup_key: device_id
      version: "demo-v1"
      on_lookup_error: REFER

  models:
    - id: card_fraud_detection_model
      name: In-house Card Fraud Detection Model
      version: "demo-v1"
      output:
        field: fraud_score
        type: integer
        minimum: 0
        maximum: 999
      on_inference_error: REFER

decision_flow:
  mode: first_match

  steps:
    - id: check_fraudulent_merchant
      type: list_match
      list_ref: fraudulent_merchant_list
      input_field: merchant_id
      when_matched:
        decision: DECLINE
        reason_code: FRAUDULENT_MERCHANT_MATCH
        explanation: Merchant is present in the known fraudulent merchant list.
        stop: true

    - id: check_fraudulent_device
      type: list_match
      list_ref: fraudulent_device_list
      input_field: device_id
      when_matched:
        decision: DECLINE
        reason_code: FRAUDULENT_DEVICE_MATCH
        explanation: Device is present in the known fraudulent device list.
        stop: true

    - id: invoke_card_fraud_model
      type: model_inference
      model_ref: card_fraud_detection_model
      output_field: fraud_score

    - id: decline_high_score
      type: score_band
      score_field: fraud_score
      range:
        min: 900
        max: 999
        include_min: true
        include_max: true
      decision: DECLINE
      reason_code: MODEL_SCORE_DECLINE
      explanation: Model fraud score is between 900 and 999.
      stop: true

    - id: refer_medium_high_score
      type: score_band
      score_field: fraud_score
      range:
        min: 800
        max: 899
        include_min: true
        include_max: true
      decision: REFER
      reason_code: MODEL_SCORE_REFER
      explanation: Model fraud score is between 800 and 899.
      stop: true

    - id: approve_default
      type: default
      decision: APPROVE
      reason_code: MODEL_SCORE_APPROVE
      explanation: No blacklist match and model score is below 800.
      stop: true

outputs:
  - decision
  - reason_code
  - explanation
  - fraud_score
  - matched_step_id
  - strategy_version

DSL 设计时需要保留的关键概念

概念为什么重要
first_match / stop明确规则执行顺序和短路行为，防止不同 Runtime 出现不同结果。
list_ref / model_ref将业务逻辑与具体名单、模型资产解耦。
on_lookup_error / on_inference_error将失败处理显式化，避免隐含的 fail-open 或 fail-closed。
range 边界明确 800、899、900、999 的归属，消除歧义。
reason_code / explanation支持审计、案件调查、业务确认和测试。
matched_step_id支持 traceability，便于确认到底命中了哪一步。

六、Layer 3：第一版仅用 Shortcut / Template 展示

第一版可以不实现真正的通用 compiler。系统只需识别当前 demo 的 DSL 结构， 然后套用预先准备好的 Janino、BigQuery SQL 和 PySpark 模板，快速让用户看到结果。

1. Java / Janino 风格示例

// Demo shortcut generated from the Layer 2 specification.
// The surrounding runtime context is assumed to provide list and model services.

if (listService.contains("fraudulent_merchant_list", transaction.getMerchantId())) {
    return DecisionResult.decline(
        "FRAUDULENT_MERCHANT_MATCH",
        "Merchant is present in the known fraudulent merchant list."
    );
}

if (listService.contains("fraudulent_device_list", transaction.getDeviceId())) {
    return DecisionResult.decline(
        "FRAUDULENT_DEVICE_MATCH",
        "Device is present in the known fraudulent device list."
    );
}

int fraudScore = modelService.predictScore(
    "card_fraud_detection_model",
    transaction,
    featureContext
);

if (fraudScore >= 900 && fraudScore <= 999) {
    return DecisionResult.decline(
        fraudScore,
        "MODEL_SCORE_DECLINE",
        "Model fraud score is between 900 and 999."
    );
}

if (fraudScore >= 800 && fraudScore <= 899) {
    return DecisionResult.refer(
        fraudScore,
        "MODEL_SCORE_REFER",
        "Model fraud score is between 800 and 899."
    );
}

return DecisionResult.approve(
    fraudScore,
    "MODEL_SCORE_APPROVE",
    "No blacklist match and model score is below 800."
);

2. BigQuery SQL 风格示例

-- Demo shortcut for offline replay / simulation.
-- Assumed inputs:
--   transactions
--   fraudulent_merchant_list
--   fraudulent_device_list
--   card_fraud_model_scores

WITH enriched AS (
  SELECT
    t.transaction_id,
    t.merchant_id,
    t.device_id,
    ms.fraud_score,
    fm.merchant_id IS NOT NULL AS merchant_blacklisted,
    fd.device_id IS NOT NULL AS device_blacklisted
  FROM transactions t
  LEFT JOIN fraudulent_merchant_list fm
    ON t.merchant_id = fm.merchant_id
  LEFT JOIN fraudulent_device_list fd
    ON t.device_id = fd.device_id
  LEFT JOIN card_fraud_model_scores ms
    ON t.transaction_id = ms.transaction_id
)

SELECT
  transaction_id,
  fraud_score,
  CASE
    WHEN merchant_blacklisted THEN 'DECLINE'
    WHEN device_blacklisted THEN 'DECLINE'
    WHEN fraud_score BETWEEN 900 AND 999 THEN 'DECLINE'
    WHEN fraud_score BETWEEN 800 AND 899 THEN 'REFER'
    ELSE 'APPROVE'
  END AS decision,
  CASE
    WHEN merchant_blacklisted THEN 'FRAUDULENT_MERCHANT_MATCH'
    WHEN device_blacklisted THEN 'FRAUDULENT_DEVICE_MATCH'
    WHEN fraud_score BETWEEN 900 AND 999 THEN 'MODEL_SCORE_DECLINE'
    WHEN fraud_score BETWEEN 800 AND 899 THEN 'MODEL_SCORE_REFER'
    ELSE 'MODEL_SCORE_APPROVE'
  END AS reason_code
FROM enriched;

3. 可选：DataProc / PySpark 风格示例

# Demo shortcut for batch replay on Spark / DataProc.

from pyspark.sql import functions as F

result = (
    transactions
    .join(fraudulent_merchant_list.withColumn("merchant_blacklisted", F.lit(True)),
          on="merchant_id", how="left")
    .join(fraudulent_device_list.withColumn("device_blacklisted", F.lit(True)),
          on="device_id", how="left")
    .join(card_fraud_model_scores, on="transaction_id", how="left")
    .withColumn(
        "decision",
        F.when(F.col("merchant_blacklisted") == True, F.lit("DECLINE"))
         .when(F.col("device_blacklisted") == True, F.lit("DECLINE"))
         .when(F.col("fraud_score").between(900, 999), F.lit("DECLINE"))
         .when(F.col("fraud_score").between(800, 899), F.lit("REFER"))
         .otherwise(F.lit("APPROVE"))
    )
)

4. 第一版 shortcut 的实现建议

Layer 2 DSL
   ↓
Recognise known demo pattern
   ↓
Fill pre-built templates
   ├── JaninoTemplate
   ├── BigQuerySqlTemplate
   └── PySparkTemplate

这种做法不会妨碍后续演进。等 Layer 1 和 Layer 2 的形式稳定以后，再逐步将模板替换为 deterministic generator、AST compiler 或 target adapter。

七、建议交给 Codex 的首轮开发顺序

Iteration 0：先做可见界面

  • 一个 Streamlit 页面；
  • 左侧输入 Business Intent；
  • 中间显示 Ambiguities 与 Clarification Questions；
  • 右侧显示 DSL YAML、决策图和三个 Layer 3 标签页；
  • 第一版可以使用固定 demo 内容。

Iteration 1：把 Layer 2 做成真实数据模型

  • 使用 Pydantic 定义 DSL / IR；
  • 支持 YAML 和 JSON 输出；
  • 增加字段校验、范围校验和 required fields；
  • 从同一语义对象渲染 DSL 与 DAG。

Iteration 2：实现 Layer 1 交互

  • 自然语言提取初始意图；
  • 标记不确定字段；
  • 生成 clarification questions；
  • 用户回答后更新 Canonical Semantic Model；
  • 保存每次修改和确认记录。

Iteration 3：模板化 Layer 3

  • 准备 Janino、BigQuery SQL 和 PySpark 三份模板；
  • 将 DSL 中的 list、model、score band、action 和 reason code 填充进去；
  • 不接真实 Runtime；
  • 只用于演示可移植性和可读性。
