FDX Horizon PoC：四层架构梳理与下一步建议

基于当前四张架构图，对 Fraud System 五大能力域、Horizon 四层产物转换链、 Verification Gate、Runtime 边界以及首个 PoC 切入方式进行统一整理。

整理日期：2026年8月1日 · 适合离线阅读、内部讨论与方案分享

核心判断：这不是一个简单的“自然语言生成规则”工具，而是一个 Fraud Decision Authoring and Portability PoC。 其核心资产应当是一个稳定、无歧义、可验证、可图形化、可编译到多种目标平台的统一语义层。

一、当前实际上存在两套相互正交的架构

1. Fraud System 的五大能力域

第一张和第四张图表达的是整个 Fraud System 的业务与技术能力全景：

1. Data Ingestion

接入外部供应商、内部支付系统、核心银行平台及其他事件来源。

2. Real-time Decisioning

在低延迟、高吞吐约束下执行欺诈规则、模型和实时或周期性指标。

3. Case Management

管理告警、转介、调查和案件闭环。

4. Data Repository

保存历史数据、审计数据、回放样本、调查数据和运营报表数据。

5. Data Science

支持规则和模型的开发、训练、仿真、部署、复用与治理。

3. Horizon PoC 的四层产物转换链

第二、三张图表达的不是 Fraud System 的另一套业务分区，而是从业务意图到运行时产物的生命周期：

Layer 1: Business Intent
        ↓ semantic interpretation
Layer 2: Canonical Fraud Decision Specification
        ↓ compilation / generation
Layer 3: Target-specific Technical Artifacts
        ↓ verification, approval and deployment
Layer 4: Runtime Execution

两套架构的关系可以概括为：

FDX Horizon
位于五大能力域中的 Data Science

但 Horizon 的端到端工作流
从业务作者开始，最终连接到 Real-time Decisioning Runtime

二、四层结构的进一步整理

Layer 1：Business Authoring Layer

主要用户是 Fraud Analyst、Business Analyst、Risk SME。他们使用英语描述检测意图，但不应完全依赖无限制的自由聊天。

这一层应提供：

Guided Prompt 模板 Copilot 字段提示 歧义检测 追问澄清
Block a card transaction when there are at least five declined transactions from the same card within ten minutes, followed by a successful transaction above USD 500.

系统不应立刻生成 Java 或 SQL，而应先确认：

  • “same card”具体使用哪个实体键；
  • 五次失败是否包含当前交易；
  • 十分钟按 event time 还是 processing time；
  • 成功交易是否必须发生在第五次失败之后；
  • 不同币种怎样统一换算；
  • 迟到事件和乱序事件怎样处理；
  • Block 是硬拒绝，还是只输出风险建议。

Layer 1 的输出应是经过澄清的 Fraud Detection Intent，而不是代码。

Layer 2：Semantic Authoring Layer

这是整个方案中最重要、最值得沉淀为平台资产的一层。

建议不要只称为 DSL，而是采用更明确的概念，例如：

  • Canonical Fraud Decision Specification，CFDS
  • Fraud Decision Intermediate Representation，FDIR

因为它不仅包含语法，还需要承载完整语义：

决策语义

  • 规则条件与优先级
  • 模型调用与阈值
  • 评分组合
  • 最终 action / decision
  • explanation 和 reason code

数据与时序语义

  • 实体与字段定义
  • 时间窗口和聚合
  • 事件顺序
  • 缺失值与单位
  • event-time / late event
  • feature freshness
所有后端都应消费 Layer 2 的统一语义规范，而不是让 LLM 从英语分别直接生成 BigQuery SQL、Janino、PySpark 或其他实现。否则不同后端很容易出现语义漂移。

与 DMN / FEEL 的关系

最值得优先参考的是 OMG DMN 与 FEEL。DMN 擅长表达 business decision、decision table 和 decision dependency graph；FEEL 提供较为标准化的表达式语义。

但 Fraud Detection 还需要额外表达：

  • 滚动时间窗口、distinct count、event sequence、absence of event；
  • 在线特征查找、point-in-time semantics、late and out-of-order event；
  • 模型调用、规则停止策略、多阶段评分组合；
  • 实时 Runtime 的状态和性能约束。
Fraud DSL / Canonical Specification
├── 借鉴 DMN 的 decision graph
├── 借鉴 FEEL 的 expression semantics
├── 增加 fraud-specific event/window/feature constructs
└── 可导出 DMN-compatible subset

Layer 3：Realisation Layer

Janino、ONNX、BigQuery SQL、PySpark/DataProc 可以位于这一层，但不宜作为性质完全相同的产物并列。

3A. Rule Realisation

  • Janino expression / generated Java
  • Drools DRL
  • BigQuery SQL / Flink SQL
  • PySpark
  • 平台专用 Rule JSON / YAML

3B. Feature Realisation

  • BigQuery feature SQL、dbt model
  • PySpark feature pipeline
  • Flink stateful feature operator
  • Online feature mapping
  • Redis / Memorystore lookup definition

3C. Model Realisation

  • ONNX model binding
  • 模型 URI 与版本
  • 输入 feature signature
  • preprocessing、threshold、calibration
  • checksum 与兼容性信息

3D. Decision Package and Deployment Metadata

rules.yaml、feedback.yaml、explanations.yaml、 map-operators.yaml、features-map.yaml 更像 deployment package， 而不是 Janino 本身。 

Java/Flink Decision Package
├── Janino expressions / compiled rule functions
├── rules.yaml
├── feature-map.yaml
├── operator-map.yaml
├── explanations.yaml
└── deployment manifest

Verification and Conformance Gate

将 Gate 放在 Layer 3 与 Layer 4 之间是合理的，但它不应只检查“是否能编译”。

1. Structural Validation

  • Schema 和必填字段
  • 类型与引用完整性
  • Feature / Model / Rule 是否存在
  • DAG 是否有环

2. Semantic Validation

  • 窗口是否合法
  • 规则冲突与重叠
  • 遗漏路径和不可达路径
  • 单位、币种和 null handling
  • 是否错误引用未来数据

3. Target Validation

  • SQL compile / dry run
  • Java / Janino compile
  • PySpark plan validation
  • ONNX input signature
  • Runtime capability check

4. Behavioural Equivalence

  • 相同输入数据
  • 不同后端执行
  • 比较 feature、rule hit、score、decision、explanation
  • 使用 Golden Test Dataset
Canonical specification
        ├── compile to Java/Flink
        ├── compile to BigQuery SQL
        └── compile to PySpark

same input fixtures
        ↓
compare features, rule hits, score, decision and explanation
因此，这一层更适合命名为 Verification and Conformance Gate。

Layer 4：Runtime Deployment Layer

Decision Runtime

  • 接收 transaction context；
  • 读取在线 feature / profile；
  • 执行规则、调用模型和进行 score aggregation；
  • 生成 action、decision、reason code、explanation 和 audit trace；
  • 支持版本激活、hot reload 和 rollback。

Online Feature and Profile Service

  • point feature、rolling window state、profile 和 list lookup；
  • velocity feature、预计算聚合和 feature freshness；
  • Redis / Memorystore、Flink keyed state、本地 cache 或外部 feature service。
Online Feature Serving
├── Stream-computed state
├── External feature store
├── Profile service
├── Reference/list cache
└── Feature freshness metadata
Runtime Engine、Flink state、Online Feature Serving 基础设施可以属于 RAPIDS 或其他平台。 Horizon 更适合负责 authoring、semantic specification、generation、verification、approval 和 release package，而不是把所有运行时能力都纳入自身范围。

三、建议对当前架构做的三个核心调整

调整一：Layer 2 不只是一个 DSL 文件，而是统一语义模型

Canonical Semantic Model
├── Textual DSL / YAML View
├── Graph / DAG View
└── Business Form / Decision Table View

三种形式应是同一个语义模型的不同呈现，而不是彼此独立地来回转换。

          Canonical in-memory model
          /          |           \
       DSL        DAG view      Form/table

调整二：区分 Authoring、Compilation 和 Deployment Ownership

Horizon 适合负责

  • Business authoring
  • Semantic specification
  • Target artifact generation
  • Verification
  • Approval workflow
  • Release package creation

不一定由 Horizon 负责

  • Runtime transaction processing
  • Flink state management
  • Online feature infrastructure
  • Case management

Layer 4 的标题可以调整为：Target Runtime and Deployment Integration。

调整三：第一个 PoC 不要同时实现所有后端

目标架构可以支持很多后端，但首个 PoC 建议只做一个纵向切片：

English
→ Fraud DSL
→ DAG
→ Java / Janino package
→ lightweight local runtime

再增加一个性质不同的离线后端：

Fraud DSL
→ BigQuery-compatible SQL

这样即可证明一个核心命题：同一份 Canonical Specification 能生成两类不同的目标产物， 且结果可以被验证为语义一致。

四、建议的第一个 PoC 场景

第一版不建议从模型训练切入，而应选择一个能同时验证窗口、顺序、特征、规则和解释的 Fraud Scenario。

Card Testing followed by High-value Purchase

When:
  at least 5 declined card-not-present transactions
  from the same card
  across at least 3 merchants
  within 10 minutes

followed by:
  a successful transaction
  with amount converted to USD >= 500
  within 5 minutes

then:
  risk_score += 70
  decision = REFER
  reason_code = CARD_TESTING_FOLLOWED_BY_PURCHASE

这个场景能够同时验证：

  • 自然语言歧义处理
  • entity key
  • distinct count
  • rolling window
  • event sequence
  • currency normalization
  • feature dependency
  • decision 和 explanation
