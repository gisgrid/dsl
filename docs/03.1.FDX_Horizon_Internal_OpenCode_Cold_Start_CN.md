## 2. 项目核心思想

这不是一个简单的“自然语言生成代码”项目，而是在验证以下链路：

```text
Layer 1: Business Intent
        ↓ semantic interpretation, ambiguity detection and clarification
Layer 2: Canonical Fraud Decision Specification
        ↓ compilation / generation
Layer 3: Target-specific Technical Artifacts
        ↓ verification, approval and deployment integration
Layer 4: Runtime Execution
```

### Layer 1：Business Intent

Fraud Analyst、Business Analyst 或 Risk SME 使用自然语言描述 Fraud Detection 需求。系统负责识别意图、发现歧义、提出 clarification questions，并让用户补充自然语言或结构化答案。

### Layer 2：Canonical Fraud Decision Specification

这是当前 PoC 最重要的核心资产。它应当：

- 结构化；
- 可审阅；
- 尽量无歧义；
- 与目标技术栈无关；
- 可渲染为 YAML 和 Decision Graph；
- 可作为 Layer 3 多种实现的统一语义来源。

重要原则：

> YAML、Decision Graph 和 Layer 3 Preview 应来自同一个 Pydantic semantic object，不能各自维护一份可能漂移的逻辑。

### Layer 3：Target-specific Technical Artifacts

当前主要是模板化 Preview，而不是 production compiler：

- Java / Janino / Flink Preview
- GCP BigQuery SQL Preview
- GCP DataProc / PySpark Preview
- AWS SageMaker AI for Dragon（当前可为 future placeholder）

### Layer 4：Runtime Execution

当前 PoC 不实现真正 Runtime Deployment。不要擅自扩展到真实 Flink、BigQuery、DataProc、SageMaker、Feedzai、Redis、Foundry、RBAC、HA 或性能工程。

## 3. 当前 Demo 场景

当前 Demo 是“规则 + 模型”的 Fraud Decision Strategy：

1. Merchant 命中 known fraudulent merchant list → `DECLINE`
2. 否则 Device 命中 known fraudulent device list → `DECLINE`
3. 否则调用自研 Card Fraud Detection Model
4. 模型输出整数分数 `0–999`
5. `900–999` → `DECLINE`
6. `800–899` → `REFER`
7. `0–799` → `APPROVE`

DSL 还应体现 first-match / stop、list resource、model resource、model version、score range、inclusive boundaries、reason code、explanation、错误处理、output fields 和 matched step traceability。

## 5. 图形实现原则

Decision Graph 不能只显示 plain text 或 Mermaid source。期望路径：

```text
FraudDecisionSpec
        ↓
Python graph view model
        ↓
Self-contained SVG or HTML
        ↓
Streamlit component rendering
```

建议使用：

```python
st.components.v1.html(...)
```

要求：

- 完全离线；
- 不使用 CDN；
- 不依赖外部 Mermaid runtime；
- 不发起网络请求；
- Windows 与 Linux 均可运行；
- 图中节点、分支、score band、decision 和 reason code 从 semantic model 获取；
- renderer 尽量保持为可测试的纯函数。

当前至少支持：`list_match`、`model_inference`、`score_band`、`default`。

## 6. 公司环境中的启动步骤

先确认 Python：

```bash
python --version
python3 --version
```

然后在 repo 根目录执行：

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e '.[dev]'
```

运行检查：

```bash
pytest
python -m compileall src app.py tests
python -c "import app; print('app import ok')"
```

启动 Streamlit：

```bash
python -m streamlit run app.py \
  --server.address 0.0.0.0 \
  --server.port 8501 \
  --server.headless true \
  --server.fileWatcherType none
```

不要只绑定 `127.0.0.1`。Agent 运行在 Windows 主机中的 Linux 容器内，绑定 `0.0.0.0` 更便于端口转发。

## 7. 重点：Windows 主机访问 Linux 容器中的 Streamlit

不要只说“Streamlit 已启动”。必须和用户一起确认 Windows 浏览器能否真正访问。

### 7.1 容器内部验证

```bash
curl -I http://127.0.0.1:8501
ss -lntp | grep 8501
```

期望监听：

```text
0.0.0.0:8501
```

如果容器内部都不能访问，先解决应用启动问题。

### 7.2 先识别容器类型

请向用户确认环境属于哪种：

- VS Code Dev Container
- Docker Desktop / docker run
- Docker Compose
- WSL2 容器
- Kubernetes / OpenShift Pod
- 公司自研开发容器
- 远程 Linux 开发机

不要在未确认环境时武断给出唯一方案。

### 7.3 常见端口转发方式

#### VS Code Dev Container

检查 VS Code 的 `PORTS` / `Forwarded Ports` 面板，将容器端口 `8501` 转发到 Windows。用户通常访问：

```text
http://localhost:8501
```

必要时可检查 `.devcontainer/devcontainer.json` 是否允许：

```json
{ "forwardPorts": [8501] }
```

修改前先确认公司环境策略。

#### Docker Desktop / docker run

容器创建时通常需要：

```bash
-p 8501:8501
```

如果现有容器没有映射端口，可能需要调整启动配置或重建容器。不要擅自重建公司容器，先与用户确认。

#### Docker Compose

检查：

```yaml
ports:
  - "8501:8501"
```

#### WSL2

先尝试：

```text
http://localhost:8501
```

如果失败，再检查：

```bash
hostname -I
```

并尝试 `http://<WSL-IP>:8501`，但要考虑公司安全策略。

#### Kubernetes / OpenShift / Remote Container

可能需要 IDE port forwarding、`kubectl port-forward`、OpenShift port-forward、公司代理 URL 或 Route。不要自行创建公网暴露。

### 7.4 如果端口被占用

```bash
ss -lntp | grep 8501
```

可以临时尝试 `8502`，但必须同步更新端口转发。

### 7.5 出现访问问题时应报告

请明确告诉用户：

1. Streamlit 是否成功启动；
2. 监听地址和端口；
3. 容器内 curl 是否成功；
4. 当前判断的容器类型；
5. 用户在 Windows / IDE 上需要做什么；
6. 下一步应该访问哪个 URL。

## 8. 跨平台注意事项

### 文件名大小写

Linux 区分大小写，import 必须与真实文件名完全一致。

### 路径处理

不要写死 Windows 反斜杠路径，统一使用 `pathlib.Path`。

### 编码

读取文本时明确 `encoding="utf-8"`。

### 换行符

Shell 脚本使用 LF。

### 虚拟环境

不要提交 `.venv/`。

### 外部资源

公司环境可能无法访问公网。应用运行时不得依赖 CDN、Google Fonts、远程 Mermaid、网络图片或外部 API。

Python 包安装是否需要公司内部镜像，应和用户确认。

## 10. 后续开发原则

1. Layer 1 和 Layer 2 仍是重点。
2. 不要过早实现完整 compiler。
3. UI 逻辑不要污染 semantic models。
4. graph renderer 不要依赖 Streamlit session state。
5. Layer 2 是单一语义来源。
6. 不要静默改变 DSL 语义。
7. 修改 DSL 时同步更新 model、YAML、graph、templates、validation、examples、tests 和 docs。
8. 新增 production 场景时逐步建立 Rule / Model Inventory、Capability Matrix、Golden Rule Corpus、Replay fixtures 和 Behavioural comparison。
9. 不支持的 production 语义要显式标记，不要猜测转换。
10. 所有改动先测试，再汇报，确认后再 commit / push。

## 11. 最重要的冷启动目标

当前目标不是证明 DSL 已覆盖所有 production 规则，而是：

- 清晰演示 Horizon 思想；
- 验证 Business Intent → Clarification → Canonical DSL / IR；
- 从同一个语义对象生成 YAML、Decision Graph 和 Layer 3 Preview；
- 为后续 Production Coverage、Replay 和 Runtime Integration 建立基础。

你在公司环境中的第一项真正任务是：

> 在 Linux 容器中成功启动 Streamlit，并与用户一起让 Windows 主机浏览器能够访问和操作它。
