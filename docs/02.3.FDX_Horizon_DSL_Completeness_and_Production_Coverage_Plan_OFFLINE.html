02.3 FDX Horizon DSL 完备性与 Production Coverage 计划

DSL 的“完备性”不能通过字段数量或设计评审直接宣布。可信的证明方式是：Production Rule / Model Inventory + Capability Matrix + Golden Rule Corpus + Differential Replay + Behavioural Equivalence。

1. 完备性的定义2. Production 盘点3. Golden Rule Corpus 4. 量化指标5. 模型支持6. 双轨回放 7. 扩展机制8. 后续计划

一、先定义“DSL 完备”是什么意思

表达完备性

现有 production 规则中的每一种语义构造，DSL 是否有明确表达。

  • 字段比较、AND / OR / NOT
  • 黑白名单与 profile lookup
  • 优先级、first-match、stop / continue
  • 窗口聚合、distinct count、事件序列
  • 模型调用、多模型编排、fallback
  • reason code、explanation、error handling

语义完备性

  • 边界是否包含
  • null 如何处理
  • lookup / inference 失败如何处理
  • event time、时区、late event
  • 多条规则同时命中如何解决
  • score 是覆盖、累加还是取最大值

行为等价性

相同 replay 数据在生产引擎与 DSL 实现中的结果是否一致。

  • decision
  • score
  • matched rule / step
  • reason code
  • model version
  • fallback path

Runtime Contract 完备性

  • required features 与 freshness
  • model artifact / endpoint / version
  • timeout、retry、fallback
  • latency class、audit fields
  • 部署兼容性
当前 Layer 1 / Layer 2 PoC 不必立刻覆盖所有 Runtime Contract，但应预留清晰边界，避免未来只能通过嵌入任意 Java 或 Python 来绕过 DSL。

三、建立 Golden Rule Corpus

优先选取 20–50 条覆盖面最大的规则，而不是一次迁移全部 production 规则。

基础规则

字段比较、名单命中、默认动作。

规则 + 模型

黑名单、模型调用、分数区间、fallback。

时间窗口

velocity、rolling count、distinct count。

事件序列

先失败后成功、absence of event、顺序约束。

Profile / Feature

设备、客户、商户 profile 与 freshness。

复杂编排

多模型、多阶段评分、规则冲突与回退路径。

四、量化完备性

Rule Coverage

完整表达规则数 ÷ 评估规则总数。

Construct Coverage

已支持语义构造数 ÷ 识别构造总数。

Behaviour Match

decision、score、reason code、matched path 的一致率。

Unsupported Rate

Unsupported、Ambiguous、Platform-specific、Requires extension。

指标初期目标示例成熟目标示例
Rule Expression Coverage≥ 80%≥ 95%
Construct Coverage≥ 75%≥ 95%
Decision Match Rate≥ 99%100% 或批准的例外
Reason Code Match Rate≥ 95%≥ 99.9%

这些数字仅用于规划示例，最终阈值应结合风险等级、迁移策略与验收要求确定。

五、模型支持的重点是 Model Binding Contract

DSL 通常不描述 XGBoost 树或神经网络内部结构，而应描述输入、输出、版本、调用、异常处理和 post-model decision。

model:
  id: card_fraud_detection_model
  version: v7
  input_schema:
    feature_set: card_fraud_v7_features
    required_count: 172
  output:
    field: fraud_score
    type: integer
    minimum: 0
    maximum: 999
  runtime:
    timeout_ms: 50
    on_timeout: REFER
    on_inference_error: REFER
    on_missing_feature: REFER
  post_model_decision:
    - range: [900, 999]
      decision: DECLINE
    - range: [800, 899]
      decision: REFER
    - default:
      decision: APPROVE

六、最终证明方法：双轨回放

              └── fallback path               └── fallback path

不一致样本应分类为：DSL 表达缺失、转换器错误、原规则隐式语义、Runtime 差异、时序差异、feature / model 版本差异，或 production 实现本身的问题。

七、允许“明确不支持”，不要假装完备

Core DSL
+ Controlled Extensions
+ Explicit Unsupported Result
support_status:
  level: unsupported
  reason: requires_event_sequence_with_negative_pattern
extensions:
  - namespace: fdx
    type: custom_operator
    name: shared_device_ring_score
    version: "1.0"
不建议允许任意嵌入 Java、Python 或 SQL 作为通用逃生口，否则 DSL 会失去统一语义、可验证性与可移植性。

└── scenario_name/
    ├── fraud_spec.yaml
    ├── input_events.json
    ├── expected_decisions.json
    ├── production_outputs.json
    └── comparison_report.json

Phase D：依据真实缺口扩展 DSL

只有 Production Corpus 暴露出真实语义缺口时，才扩展 DSL，不建议提前设计大量没有 production 依据的语法。

当前 PoC 仍应优先打磨 Layer 1 → Layer 2 的交互质量；Production Coverage 可作为并行轨道，用真实规则语料逐步验证和塑造 DSL。
